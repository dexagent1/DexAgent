# Building new skills and verifiers

The library is self-evolving: capabilities you build now are reused on later videos. These rules make a new tool worth keeping.

1. **Never modify an existing tool.** Existing skills and verifiers are frozen: other stages and earlier results depend on them. To change behaviour, `library_read` the tool, then `library_create` a NEW tool under a new, more specific name (`measure_object_color` -> `measure_object_color_hsv`, or a name that says what is new). `library_create` refuses names that already exist.
2. **Generalize.** A tool is a parameterized function for a class of inputs, never for this one video or object: no hard-coded frame numbers, pixel boxes, colours, object names or file paths. Everything specific is a parameter with a sensible default. A constructor is parameter-controlled (sizes, counts, colours, mechanism properties) and refuses unknown parameters.
3. **Prove it on variations before it counts.** Your `test_source` must run the tool on at least three distinct variations (different inputs, sizes, parameters, or synthetic cases that exercise the edge behaviour) and print one `[PASS] <case>` line per passing case, exit non-zero on any failure. It imports the tool the way the library does: `from tool_library.skills.<name> import <name>` (or `tool_library.verifiers.<name>`), after `sys.path.insert(0, str(Path(__file__).resolve().parents[2]))` so the test runs from anywhere. `library_create` runs the test and keeps the tool only if it passes. A tool that works on one case is not a tool.
4. **One file, documented like the rest.** The file starts with a module-level `TOOL = {...}` literal: `name` (== file name), `title`, `type` (`skill` | `verifier`), `category` (skills: Trajectory & Execution, Object Reconstruction, Perception & Grounding, Scene Runtime & Rendering, Grasp & Poses, Measurements; verifiers: Task & Rollout Gates, Grasp Stress Tests, Reconstruction Mechanism Tests, Episode Audits, Scene Assertions, Scene Compile Checks), `summary` (one sentence), `description` (what it does, how it decides, what it assumes), `inputs` and `outputs` (lists of `{name, type, description}`, accurate), `status: "tested"`, `entrypoint` (the function's name, == name), optional `requirements`, `tags`, `used_in` (the tasks the tool was made for or used on: a paper task's name or your own task's, e.g. the run's task name), `cli`. No dates or time information anywhere. Import only `tool_library.common`, the standard library and third-party packages; never another project's code; no machine-specific paths.
5. **Verifiers return a report.** A verifier returns a dict with `ok` (bool), `issues` (list of strings a model can act on, naming what to change) and the measurements it based the verdict on. It never raises on a bad input it was designed to judge; it reports.
6. **Skills return what they produced.** A skill returns a dict with paths of files it wrote and the facts it measured, JSON-serializable, never a bare print.
7. **Fail loudly on misuse.** Unknown parameters, impossible combinations and missing inputs raise `ValueError` with a message that names the parameter to change.
8. **Keep the budget in mind.** Build a tool when the capability is missing and will be needed again (this video has several instances, or the stage contract calls for it). Do not build one to wrap a single `run_python` line.
